### 1단계: 프록시 주소를 파이썬 사전 규격에 맞춰 정리하기

실제 웹 페이지의 구조를 분석해 주는 도구가 뷰티풀수프라면, 웹에 접속해 문서를 받아오는 심부름꾼은 리퀘스츠 라이브러리입니다. 프록시를 쓰려면 이 심부름꾼에게 어떤 통로를 거쳐 가야 할지 명확한 주소록을 쥐여주어야 합니다.

보통 프록시 서비스 업체에서 주소와 포트 번호를 받아오게 됩니다. 만약 보안 인증이 필요한 유료 프록시라면 사용자 이름과 비밀번호까지 함께 받게 되죠. 이 정보들을 파이썬의 사전 형태로 정돈해 두는 것이 출발점입니다.

일반 웹 접속용 주소와 보안 웹 접속용 주소를 각각 지정해 주어야 합니다. 주소 앞에는 통신 규약 이름을 붙이고, 인증 정보가 있다면 골뱅이 기호 앞에 계정과 비밀번호를 나란히 적어 넣으면 됩니다. 이렇게 한 번 깔끔하게 사전을 만들어 두면 나중에 주소가 바뀌더라도 이 부분만 수정하면 되니 관리가 무척 편해집니다.

### 2단계: 네트워크 요청 시점에 프록시 주머니 건네주기

사전 준비가 끝났다면 이제 데이터를 가져오는 요청 단계에서 이 설정을 밀어 넣어줄 차례입니다.

많은 분이 착각하는 부분 중 하나가 뷰티풀수프 자체에 프록시 설정 기능이 있다고 생각하는 점입니다. 뷰티풀수프는 이미 받아온 글자 뭉치에서 원하는 태그를 기가 막히게 골라내는 파싱 도구일 뿐, 인터넷망을 돌아다니며 데이터를 긁어오는 기능은 전적으로 리퀘스츠가 담당합니다.

따라서 웹 페이지를 가져오는 함수를 호출할 때, 앞서 정돈해 둔 프록시 사전을 옵션 인자 자리에 그대로 전달해 주면 됩니다. 이때 제가 실무에서 뼈저리게 느낀 팁이 하나 있습니다. 반드시 대기 시간 제한을 몇 초 정도로 짧게 걸어두어야 한다는 점입니다. 느리거나 죽어버린 프록시 서버에 걸리면 프로그램이 멈춘 채 무한정 기다리게 되기 때문입니다. 이렇게 안전하게 받아온 텍스트 응답을 평소처럼 뷰티풀수프의 재료로 넘겨주면, 대상 웹사이트는 제 컴퓨터가 아닌 프록시 서버의 방문으로 인식하게 됩니다.

### 3단계: 죽은 연결을 걸러내고 새 통로로 갈아타는 예외 처리 만들기

프록시 서버는 공공재처럼 쓰는 무료 서버든 돈을 내고 쓰는 서버든 간에 언제든 예기치 않게 연결이 끊어질 수 있습니다.

단 하나의 프록시 주소만 믿고 수천 페이지를 긁다가는 중간에 서버가 응답하지 않아 전체 프로그램이 멈춰버리는 낭패를 봅니다. 제가 팀 내 데이터 파이프라인을 구축하면서 가장 공들였던 지점도 바로 이 예외 상황을 매끄럽게 넘기는 작업이었습니다.

여러 개의 프록시 주소를 목록에 담아두고, 무작위로 하나를 골라 요청을 시도하는 반복 구조를 만들어야 합니다. 이때 발생할 수 있는 접속 오류나 시간 초과 오류를 감싸 쥐는 예외 구문을 작성하는 것이 핵심입니다. 특정 주소로 접속하다가 에러가 발생하면, 프로그램을 강제 종료하는 대신 해당 주소를 목록에서 잠시 제외하고 다른 주소로 즉시 재시도하도록 흐름을 유도하는 방식입니다.

이렇게 3단계를 탄탄하게 구성해 두면 밤새 수집기를 켜두고 퇴근해도 차단 걱정 없이 마음 편히 아침을 맞이할 수 있습니다. 작은 우회 통로 하나를 더했을 뿐인데, 데이터 수집의 안정감은 완전히 달라집니다.

## <span style="color: #8E44AD;">내 컴퓨터의 신원을 숨기는 중계소의 작동 메커니즘</span>



우리가 일상에서 택배를 보낼 때 가끔 보내는 사람의 주소를 비밀로 부치고 싶을 때가 있습니다. 이럴 때 중간에 있는 사서함이나 믿을 수 있는 지인의 집을 한 번 거쳐 배송을 보내면, 최종 수취인은 물건을 보낸 본래 출발지를 알 수 없게 됩니다. 네트워크 세상에서 이 지인 역할을 대신해 주는 친구가 바로 중계 컴퓨터입니다. 기본적으로 클라이언트가 목표 웹사이트에 접속 신호를 날릴 때, 통신망 헤더에는 보내는 이의 고유 주소가 선명하게 찍히게 마련입니다. 웹사이트 관리자는 동일한 주소에서 비정상적으로 빠른 속도로 연속 요청이 들어오는 것을 감지하면 해당 통로를 즉각 차단해 버립니다.

이러한 병목 현상을 해결하려면 출발지와 목적지 사이에 믿을 만한 중계지를 배치해야 합니다. 내 프로그램이 목적지 사이트에 직접 문을 두드리는 대신 중계지 컴퓨터에 웹 문서의 내용을 대신 받아와 달라고 부탁하는 구조를 세우는 것입니다. 목적지 사이트 관리자 화면에는 내 작업실 컴퓨터가 아니라 중계지 컴퓨터의 흔적만 남게 되므로, 본래 신원은 철저히 장막 뒤에 감춰집니다. 제가 팀 내부에서 방대한 공개 데이터를 갈무리할 때도 이 우회망을 거치도록 설계하고 나서부터는 작업 도중 접속이 끊겨 속을 끓이는 일이 눈에 띄게 줄었습니다.

이러한 기본 흐름을 파악하는 것이 바로 Beautiful Soup 기반 웹 스크래퍼에 프록시 서버 적용하기: 핵심 3단계의 출발점입니다. 데이터를 추출하는 작업 자체보다 선행되어야 하는 것은 목표 서버와의 안정적인 악수이며, 이 과정에서 발생할 수 있는 신원 노출 위험을 원천적으로 통제해야 합니다. 접속 통로를 우회시키는 것만으로도 전체적인 데이터 수집 생태계는 몰라보게 단단해지며, 장시간 돌아가는 배치 프로그램의 완주 가능성을 비약적으로 끌어올릴 수 있습니다.



## <span style="color: #8E44AD;">HTTP 통신과 파싱 엔진의 명확한 역할 분담 이해</span>



작업을 처음 시작할 때 많은 분이 흔히 겪는 혼선이 바로 파싱 도구에게 네트워크 통신 기능까지 기대한다는 점입니다. 뷰티풀수프는 엄밀히 말해 이미 내 컴퓨터 메모리 안으로 다운로드된 문서 조각을 이리저리 뒤적여 원하는 요소만 쏙쏙 발라내는 돋보기 역할을 합니다. 인터넷 바다로 나가서 웹 서버와 악수를 하고, 헤더를 주고받으며, 상태 코드를 확인하는 바깥일은 완전히 네트워크 전문 라이브러리의 몫입니다. 두 도구의 일터를 분명하게 구분 짓지 않으면 어디에 우회 주소를 등록해야 할지 길을 잃기 쉽습니다.

우리가 Beautiful Soup 기반 웹 스크래퍼에 프록시 서버 적용하기: 핵심 3단계를 차근차근 밟아 나갈 때도 이 경계선을 정확히 인식하는 작업이 선행되어야 합니다. 문을 열고 들어가서 데이터를 손에 쥐어 오는 사자는 네트워크 라이브러리이고, 그 사자가 들고 온 보자기를 풀어서 보석을 골라내는 감정사는 파서입니다. 따라서 우회 주소와 관련된 모든 네트워크 통신 규약은 돋보기가 아닌 사자의 손에 쥐여주어야 마땅합니다.

현업에서 일하다 보면 엉뚱하게 파싱 객체를 초기화하는 지점에 네트워크 설정값을 집어넣으려다 오류를 마주하는 동료들을 종종 봅니다. 통신 계층에서 먼저 우회 통로를 통해 완전한 텍스트 문서를 온전히 받아온 다음, 이를 파싱 엔진의 원자재로 넘겨주는 2단계 분리 구조를 머릿속에 도식화해 두어야 합니다. 이 구분이 명확해져야만 네트워크 문제로 응답이 오지 않는 상황과 문서 구조가 틀어져서 요소를 찾지 못하는 파싱 문제를 독립적으로 분리해서 디버깅할 수 있습니다.



## <span style="color: #16A085;">무료 공용 통로와 유료 전용 회선의 본질적인 차이</span>



처음 환경을 구축할 때 비용을 아끼고자 공개 게시판에 널려 있는 공용 우회 주소를 무작정 긁어모아 코드에 엮는 경우가 많습니다. 저 역시 수년 전 테스트 프로그램을 짤 때 공개 주소 목록 수백 개를 모아놓고 호기롭게 수집기를 돌렸던 적이 있습니다. 하지만 채 십 분도 지나지 않아 절반 이상의 서버가 응답을 멈췄고, 살아남은 몇 개조차도 거북이처럼 느린 속도로 데이터를 뱉어내며 전체 파이프라인을 멈춰 세웠습니다. 공개된 통로는 누구나 쓸 수 있다는 장점이 있지만, 그만큼 언제 문을 닫을지 모르고 악의적인 패킷 감청 위험도 도사리고 있습니다.
